# Architecture flow and data review

The local implementation supports durable dispatch and provider reconciliation, but the architecture artifacts collapse several different payloads and omit the admission phase. One synthetic probe also found that repeating a start request can return expired result content before the retention alarm removes its row.

This review covers the locally built Worker, Durable Object, SQLite store, MCP interface and provider adapters. Cloud account provisioning and live provider behavior remain pending. No external account requests or private configuration reads were performed. Implementation and model files were not edited.

## Findings

### 1. The provider conversation and owner-facing result are different payloads

**Severity: medium. Confidence: high. Challenged records: `result`, `evidence`, `voice-agent.outputs`; all generated result cards and session panels.**

The model describes the result generated by `CallEngine.view`, then also assigns that entity to the ElevenLabs conversation read and the voice agent's output. The provider does not return `telephone_status`, `delivery_verified`, an authenticated `recording_url`, or the combined cost object. The service constructs those fields after combining separate sources.

Evidence:

- [The provider response schema](../../src/providers.ts#L11) contains a conversation ID, conversation status, transcript, telephone metadata and analysis.
- [The provider transformation](../../src/providers.ts#L137) copies telephone identity, converts provider seconds to milliseconds and currency to microdollars, and maps analysis into task fields. It deliberately changes a reminder's `completed` assessment to `unknown`.
- [The Twilio transformation](../../src/providers.ts#L161) supplies separate telephone status and Twilio charges.
- [The client presentation](../../src/engine.ts#L181) combines those values, paginates transcript turns and constructs the recording route.
- `architecture/views/data/overview.json` currently lists the same `result` card both as data for the ledger-to-provider read and as the voice agent's output.

Correction: model the raw ElevenLabs conversation, raw Twilio call state and owner-facing result separately. Show the transformation into persisted `Task` JSON. Keep the provider read arrow as request direction, but make its returned payload explicit. The brief and initiation cards also need the required `task_type` and `success_criteria`, the nested `conversation_initiation_client_data`, and the array-to-JSON-string conversions from [dispatchBody](../../src/agent.ts#L74).

### 2. The call identifier is returned only after synchronous provider admission checks

**Severity: medium. Confidence: high. Challenged records: `request`, `route`, `persist`, `start`, overview journey.**

The overview moves from the owner request to persistence and outbound initiation without showing the provider dependencies that must complete before a durable call exists. This hides the first major latency and failure boundary. The outbound call itself is deferred to an alarm, but admission is not.

Evidence:

- [CallEngine.start](../../src/engine.ts#L24) awaits provider preflight before it creates or stores the task at lines 37–38.
- [LiveProviders.preflight](../../src/providers.ts#L70) issues seven concurrent reads for agent configuration, ElevenLabs number configuration, Twilio account, Twilio number routing, subscription credits, balance and destination pricing. It then validates identities, routing, configuration hash, funding and allowances.
- [Provider transport](../../src/providers.ts#L51) gives each request a 15-second timeout and rejects invalid responses.
- [CallLedger.fetch](../../src/ledger.ts#L31) awaits `start` and then saves the alarm before returning its response; [the alarm](../../src/ledger.ts#L18) later calls `tick` to dispatch.

Correction: add admission-read flows and their payload or quote entity. Explain that a new start returns the pending call ID after admission and durable alarm scheduling, while actual dialing proceeds separately. Preserve the special case that an identical existing request returns its stored result without repeating preflight.

### 3. A universal no-POST-retry statement misdescribes hangup recovery

**Severity: medium. Confidence: high. Challenged records: retry metadata on `hangup`, `callback`, `resume`, `schedule`, and other unrelated flows.**

Every existing flow carries the sentence “Outbound POST is never retried; provider reads reconcile uncertainty.” That is correct for the call-initiation POST. It is misleading for the termination path, which can repeat a POST on successive reconciliation attempts while cancellation remains requested and the provider still reports an active call.

Evidence:

- [The dispatcher](../../src/engine.ts#L55) stores `dispatching` before its one provider request. [Reconciliation](../../src/engine.ts#L96) changes a recovered dispatch marker to `dispatch_unknown` and never calls dispatch again.
- [The termination sequence](../../src/engine.ts#L119) persists cancellation intent, requests termination, reads the call again, and raises `TERMINATION_UNCONFIRMED` if it remains active.
- [Twilio termination](../../src/providers.ts#L121) is a POST. [The next reconciliation time](../../src/engine.ts#L145) remains 15 seconds for active calls, so that termination sequence can run again.
- Terminal calls waiting for prices or analysis use 60-second polling, then hourly polling after a day. Fully settled calls stop polling until expiry.

Correction: put retry ownership and cadence on the relevant flows. State that dialing is never retried, status reads are repeated, and termination requests may be repeated until provider confirmation. The callback flow should describe HTTP acknowledgement only after authoritative read, identity checks and durable persistence, rather than inheriting dispatch retry language.

### 4. Repeating a start request can expose expired results before purge

**Severity: medium. Confidence: high. Challenged claims: the report's 30-day private-content expiry and the recovery view's retention guarantee.**

If the retention alarm is delayed, an expired row can still exist in SQLite. Normal get and recording routes reject it, but the idempotent-start branch returns the stored view without checking expiry. That response can include the old summary, confirmation, unresolved questions, provider identifiers and recording URL. It does not redial, and the recording route itself still rejects the expired task.

Evidence:

- [The existing-request branch](../../src/engine.ts#L14) calls `view(existing)` directly.
- [The normal expiry guard](../../src/engine.ts#L41) rejects tasks whose `expires` timestamp has passed.
- [The request lookup](../../src/store.ts#L32) returns a stored row regardless of expiry. It reports `expired` only after [purge](../../src/store.ts#L56) moves the request hash into `expired_requests`.
- The existing retention test at [test/engine.test.ts](../../test/engine.test.ts#L122) explicitly calls `tick` before retrying, so it does not cover the delayed-alarm interval.

A standalone synthetic probe supplied an expired stored task, made no provider calls, and compared normal lookup with an identical start request. Command:

```text
./node_modules/node/bin/node --import tsx /tmp/phone-calls-retention-probe.ts
```

Actual output included:

```text
"getError": "CALL_NOT_FOUND",
"duplicateError": null,
"summary": "Synthetic retained private result",
"confirmation_details": "Synthetic confirmation",
"expires_at": "2026-11-24T05:00:00.000Z"
AssertionError [ERR_ASSERTION]: An expired duplicate must reject before returning stored results
+ actual - expected
+ undefined
- 'REQUEST_EXPIRED'
```

The probe supplied the logical time `2026-11-24T05:00:00.001Z`, one millisecond after expiry. It exited with status 1 because the retention invariant failed. Attempted checks: 1. Succeeded: 0. Failed: 1, classified as `EXPIRED_RESULT_RETURNED`. The probe is a disposable local diagnostic, not a committed regression test.

Correction: qualify the current architecture's guarantee until the duplicate-start path enforces expiry. If implementation changes are authorized, add a regression test that retries after expiry without running the alarm, then reject that path without returning task content. This review makes no claim that the defect is fixed.

## Attacked and held

- **Dispatch persistence and no redial:** source inspection supports the dispatch marker before the provider POST, recovery into `dispatch_unknown`, and continued reservation of active capacity. See [engine dispatch and reconciliation](../../src/engine.ts#L55). Tests exist for timeout recovery and a crash after the marker at [test/engine.test.ts](../../test/engine.test.ts#L54); they were inspected, not rerun in this review.
- **Callback authentication, correlation and persistence:** the [Worker callback route](../../src/index.ts#L20) verifies the signature and managed agent before invoking the coordinator. [The callback handler](../../src/engine.ts#L169) fetches the authoritative conversation, correlates identities and persists before acknowledgement. Callback bodies are not directly used to overwrite task state.
- **Cancellation evidence:** pending cancellation prevents dialing. For active calls, termination is not reported merely because an update succeeds; a subsequent provider read must show terminal state. The Twilio path runs before final ElevenLabs analysis when the Twilio call ID is known. See [engine cancellation and reconciliation](../../src/engine.ts#L114).
- **Table declarations and expiry transformations:** all four modeled tables match [the active DDL](../../src/store.ts#L16). There are no declared foreign keys. Purge retains a SHA-256 request hash, aggregates the accounted allowance by the task's UTC admission month, and records a content-free unresolved-call block before deleting task JSON. `monthly_charges` can include an unresolved reservation, so “aggregate accounted costs” is more exact than implying every value is a settled provider charge.

## Review limits

The probe exercises the actual engine with a synthetic store response. It does not prove alarm delivery timing or live storage behavior. Source inspection covered the runtime contracts, engine, provider adapters, store, coordinator, Worker routes, MCP wrapper, agent definition, architecture model, report, view guide, data cards and agent session panel. It did not inspect provider internals or deployed configuration. No live call, recording or account action was attempted.
