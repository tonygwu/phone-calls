# Call behavior and recovery

Use short factual `context` as background notes and optional `rules` for instructions the phone agent follows silently. At most 20 rules of 500 characters each are accepted. The dispatcher supplies an empty array for existing clients and stored tasks that omit the field. Keep lookup conditions, ownership checks and reviewer guardrails out of spoken facts. The agent uses short turns and one lookup identifier at a time; supplied reminder and voicemail text remains verbatim. For a reminder with a supplied voicemail message, dispatch selects a dedicated exact-message prompt. Other tasks keep the conversational prompt. Only prompt text and maximum duration can be overridden; model and tool overrides remain disabled. The caller template and installation instructions are in `docs/CLIENTS.md`.

Only the configured owner can manage calls or read recordings. The Worker validates the signed Access issuer, audience, expiry, email and subject. It rejects other hostnames and browser origins. The two provider callback paths accept signed POST requests only. Twilio recording is disabled; ElevenLabs recordings stream through an authenticated route.

The Twilio callback path also accepts the conference owner's `connect_owner` webhook tool, authenticated with a separate random token scoped to one active call. This token is supplied only through a secret dynamic header variable and is omitted from public results. Ordinary calls supply an explicitly unusable disabled header value so the saved tool has no missing variable. Every Twilio conference callback signs the exact public URL including its operation and task query parameters. Unknown inbound telephone calls still receive only a rejecting response.

Every start invocation creates a new task and a new call, including repeated inputs or `request_id` labels. Calls may overlap. There are no setup-readiness, agent-fingerprint, budget, price, balance, credit, duplicate-request, or active-call admission checks. The service does not perform automatic top-ups or account upgrades. Provider billing and account limits apply directly.

Each task is saved before dispatch. A task's status processing observes its existing call; it does not create another call. If dispatch is uncertain, inspect that task. Another start request always creates a separate call. Cancellation persists until the provider identifies the call and confirms termination.

If `owner_join` is `when_live_agent` or `when_needed`, the service creates a conference with separate business and assistant participants. The owner invitation adds a third participant after acceptance. The service permits one invitation to the configured `selfNumber`, never the callback number or a destination supplied during the conversation. A timeout or unknown result never triggers another invitation. If the owner is busy, declines, does not answer or does not press 1, the assistant and recipient remain connected. The owner hears the automation and recording disclosure and has 10 seconds to press 1. Both phone destinations ring for at most 60 seconds. The assistant remains after acceptance and the task still needs its actual success criteria. A self call or reminder cannot enable owner joining. See [owner conferences](OWNER-CONFERENCES.md).

Cancellation, the duration watchdog, and a participant disconnect close the conference and request termination of every known leg, including an owner who is still ringing. The watchdog remains active until every attempted leg has a confirmed terminal status. A creation whose identity remains unknown keeps cancellation unconfirmed and is reconciled through signed status callbacks; it is never redialed. If a late callback proves a previously rejected call exists, the service reopens cleanup and terminates that leg without dialing any missing participant. If the business disconnects, cleanup occurs on the next observation, normally within 15 seconds. The assistant's normal end_call disconnects its conference participant and ends the whole conference. Provider failures can delay cleanup. Resolved transient errors clear after successful observation; unresolved dialing and registration errors remain visible.

Call duration defaults to 180 seconds for reminders and 900 seconds for other tasks. A positive `max_duration_seconds` requests another duration without an application-level ceiling; provider limits may reject unsupported values. ElevenLabs receives the duration override, and a persistent watchdog also requests termination through Twilio after the requested duration plus the 60-second ringing allowance. Provider outages can delay watchdog execution. All due active tasks are checked concurrently every 15 seconds; completed analysis runs one task at a time while no call is active. Terminal analysis checks run every minute for a day and hourly afterward.

Call results separate telephone status from task outcome. Provider summaries do not establish mailbox receipt. Costs are reported when available and may be provisional; missing prices do not prevent result collection from finishing. There is no monthly accounting or reserved allowance. A durable observation sequence keeps older responses from replacing newer results.

Conference results include per-participant identities, telephone statuses and observed call charges. `telephone_status` and the top-level `provider.call_sid` continue to describe the business leg; the ElevenLabs conversation belongs to the separate assistant leg. Owner `accepted` means the owner pressed 1, not independent confirmation that conference audio worked. Twilio conference charges are additional and are not included in the reported participant prices. The top-level Twilio total is therefore null for conference calls.

Task briefs, results and transcripts expire 30 days after acceptance, including unresolved tasks. Expiry does not block new calls or retain duplicate-request hashes. The first use of an older database atomically copies existing call history into the simplified table and removes obsolete request, budget, and blocking tables. Call IDs, timestamps and stored contents are preserved. ElevenLabs has its separately configured 30-day retention policy; the service no longer polls that configuration before calls.

MCP bodies are limited to 64 KiB and callbacks to 2 MiB. Audio callbacks are disabled. History and transcript pages contain at most 100 records, with explicit cursors or offsets. Provider errors return sanitized categories rather than credentials or raw error bodies. Cloudflare request logging remains disabled.

An explicit HTTP 401 or 403 from the ElevenLabs outbound endpoint records `not_dispatched` with `DISPATCH_NOT_ACCEPTED` rather than polling indefinitely for a call that was not accepted. Other errors remain uncertain. A correlated provider callback that proves a call exists takes precedence even if it arrives after the rejection; observation and any requested termination resume without another outbound POST. Tool-only transcript turns may omit message text and are returned with `message: null`.

To update the existing ElevenLabs agent, run `npm run agent:plan`. This reads the selected user, workspace and agent and writes the exact nested PATCH and current configuration fingerprint to `private/agent-update/plan.json`. It creates no resources and places no calls. Review that concrete plan with a fresh adversarial reviewer, then save `{ "verdict": "ship", "planSha256": "<reviewed hash>" }` as `private/agent-review.json` and run `npm run agent:apply`. The update checks the same user, workspace, agent, configuration and repository definition before sending one PATCH. It reads the agent again and requires the exact repository prompt and all managed settings. It also checks that provider defaults, workflow and webhook routing survive.

General agent maintenance preserves installed webhook tool IDs, including `connect_owner`. A provider update that removes a tool fails the preservation readback. Tool creation and attachment remain part of the separately reviewed resource setup.

Run `npm run agent:readback` to check the current agent against the planned repository definition. Raw account and agent responses stay in `private/agent-update/`. The configuration fingerprint is maintenance evidence and does not run as call admission. If a PATCH response is lost or its readback fails, the intent journal refuses another update. Read back the live agent and reconcile the existing operation before planning or applying again. If the readback matches the desired configuration and retained controls, `agent:readback` records that reconciliation without sending another PATCH. Review a rollback as another plan using the prior repository definition. Neither Worker deployment nor provisioning updates an existing agent prompt automatically.

For a rollout that introduces reminder prompt overrides, first plan, review, apply and read back `agent:plan -- --permission-only`. That scope enables only prompt-text overrides and preserves the existing conversational configuration. Deploy and verify the Worker next, then plan, review, apply and read back the full agent update. Preserve preliminary evidence before the next plan reuses the private filenames.
